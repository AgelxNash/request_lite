# Design

## Context

Вся предметная логика уже живёт в Electron-независимых модулях main-процесса: `storage.js` (атомарная запись, отклонение мутаций заблокированного «минуя UI»), `http.js` (`buildRequest`/`sendRequest`/`cancelRequest`, таймаут 30с, лимит 10МБ), а `lib/variables.js` и `lib/curl.js` — чистые модули без единого `import`, которые smoke-тесты уже гоняют в Node. Сервер, поднятый в main-процессе, получает прямой доступ ко всему этому без IPC-прокладок. Настройки (`settings.json`) читаются через `storage.getSettings/setSettings` и уже содержат расширяемый объект. Мотивация — в proposal.md, поведение — в specs/mcp-server.

## Goals / Non-Goals

**Goals:**
- MCP-сервер (поднабор протокола: инструменты) на Streamable HTTP внутри main-процесса, нулём новых зависимостей.
- Единый писатель на диск: GUI и сервер — один процесс, гонки межпроцессных записей не возникают.
- Тестируемость серверной логики в чистом Node по образцу `scripts/smoke.mjs`.

**Non-Goals:**
- stdio-транспорт и мост-процесс (можно добавить позже поверх того же реестра инструментов).
- Ресурсы (resources), промпты и сэмплы MCP — только `tools/list` / `tools/call`.
- SSE-стриминг ответов: все операции укладываются в один HTTP-ответ.
- Мутации проектов и окружений как структур (создание/удаление/переименование) через MCP.
- Удалённый доступ: только loopback, без режимов «слушать всю сеть».
- История вызовов агента в UI (лог — в консоль main).

## Decisions

**D1. Транспорт — Streamable HTTP в main, а не stdio-мост.**
Альтернатива — stdio-сервер, запускаемый ИИ-клиентом и проксирующий к приложению через локальный сокет: совместим со всеми клиентами, но требует второго процесса, своего сокет-протокола и упаковки скрипта в electron-builder (extraResources), плюс «приложение должно быть запущено» либо дублирование логики записи. Streamable HTTP поддерживают ZCode, Claude Desktop (Connectors) и Cursor — целевые клиенты. Нулевой ценой идёт вариант SSE (2025-03-26): он устарел, не выбираем.

**D2. Своя реализация JSON-RPC поверх `node:http`, а не `@modelcontextprotocol/sdk`.**
Нужный поднабор — `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call` и диспетчер JSON-RPC ошибок — это ~250–300 строк чистого JS; SDK тянет зависимости (zod и др.) ради полной спеки (сессии, resumability, стримы), которая здесь не нужна. Риск дрейфа спеки MCP компенсируется узким поднабором и фиксированной версией протокола. Формат ответа — обычный `application/json` (спека Streamable HTTP разрешает), SSE-кодирование не пишем. Сессии (`Mcp-Session-Id`) не заводим: stateless-сервер допустим, если отвечает без заголовка сессии.

**D3. Версии протокола.**
На `initialize` отвечаем всегда последней поддерживаемой ревизией (`2025-06-18`), включая случаи, когда клиент просит более новую (например, `2025-11-25`): по спеке MCP сервер отвечает версией, которую поддерживает, а клиент решает, совместим ли он с ответом. Отклонение новой версии ошибкой (исходный вариант D3) ломает реальные клиенты — они не понижают версию сами; поднабор сервера (`initialize`/`tools`) между ревизиями стабилен.

**D4. Компоновка: `src/main/mcp.js` — три зоны в одном модуле.**
(а) HTTP-сервер и JSON-RPC-диспетчер (создание/остановка слушателя, проверка токена, роутинг `/mcp`);
(б) реестр инструментов: `{name, description, inputSchema, handler}` — единый источник для `tools/list` и `tools/call`;
(в) сами обработчики, вызывающие напрямую `storage.*`, `http.buildRequest/sendRequest`, `variables.buildVars/substitute`, `curl.*` — минуя IPC: это тот же процесс, IPC тут лишь обслуживал бы сам себя.
Экспорт: `startMcpServer(settings)`, `stopMcpServer()`, `getMcpStatus()`, `applyMcpConfig(settings)` (порт/включение — рестарт слушателя, токен — без рестарта). `index.js` после `bootstrap()` вызывает `applyMcpConfig`.

**D5. Порт по умолчанию 45460, диапазон 1024–65535.**
4545 занят echo-сервером ручного e2e; 45460 лежит рядом по мнемонике и маловероятно занят. Занятый порт → слушатель не поднимается, `getMcpStatus()` отдаёт состояние «ошибка: порт занят», UI показывает это; включённый флаг в настройках не сбрасываем (пользователь правит порт, рестарт по `applyMcpConfig`).

**D6. Токен: `crypto.randomBytes(32).hex`, сравнение `timingSafeEqual`, хранение в `settings.json`.**
Токен лежит открытым текстом рядом с остальными локальными данными — приемлемо: файл в профиле пользователя, сервер слушает только loopback, угроза — локальные процессы, от которых token-file не спасёт сильнее, чем сам факт открытого порта. Альтернатива (ключница через нативный модуль) — новая нативная зависимость, не оправдана. Токен генерируется при первом включении; перегенерация — кнопкой в блоке информации о подключении (старый мгновенно недействителен).

**D7. Подстановка переменных для `send_request`.**
Снимок сохранённого запроса прогоняется через `variables.js` со словарём включённых переменных активного окружения проекта (поле `activeEnvId` из файла проекта), затем — штатный конвейер `http.buildRequest` + `sendRequest` (auth-конвертация, лимиты, таймаут — как у отправки из UI). Импорт из `src/renderer/src/lib/*` в main безопасен: модули чистые (0 импортов), это уже проверено smoke-тестами; отдельный «общий» слой не заводим.

**D8. Ответы инструментов: компактный JSON, усечение тела 100 КБ.**
`tools/call` возвращает `{content:[{type:"text", text: JSON.stringify(результат)}]}`. Тело HTTP-ответа агенту урезается до 100 КБ с полями `truncated: true, actualSize` — иначе лимитные 10 МБ из `http.js` разом съедают контекст агента. Сетевые ошибки и таймауты — как `{error: {code, message}}` внутри успешного tool-результата (не JSON-RPC-ошибка): соединение с агентом сохраняется, это соответствует спеке.

**D9. Мутации — через последовательную очередь.**
Обработчики мутаций (создание/обновление/удаление запроса, выбор окружения) выстраиваются в простую promise-очередь внутри `mcp.js`, чтобы два параллельных вызова не interleaved-нулись read-modify-write одного файла проекта. Чтения — без очереди.

**D10. IPC: `mcp:getStatus`, `mcp:setConfig`.**
Renderer читает статус (включён/выключен/ошибка, фактический адрес) и патчит настройки (`{enabled?, port?, regenerateToken?}`) — main применяет через `applyMcpConfig` и возвращает свежий статус. Префикс `mcp:*` добавляется в список каналов AGENTS.md. Preload получает `window.api.mcp.{getStatus,setConfig}`.

**D11. UI: отдельная страница настроек.**
Страницы настроек в приложении сейчас нет (тема переключается в тулбаре) — заводим новый экран «Настройки» с точкой входа в меню приложения; перенос других настроек (темы) на него — вне скоупа этого change. В первом срезе на странице ровно два параметра MCP: тумблер включения (по умолчанию выключен) и порт (по умолчанию 45460). Токен (показ/копирование/перегенерация), состояние сервера и готовый JSON-фрагмент конфигурации ИИ-клиента (типа `{"mcpServers": {"request-lite": {"url": "http://127.0.0.1:45460/mcp", "headers": {"Authorization": "Bearer <token>"}}}}`) — не настройки, а блок информации о подключении, который появляется при включённом сервере.

## Risks / Trade-offs

- [Дрейф спеки MCP: новые обязательные поля рукопожатия] → поднабор минимален и стабилен (`initialize`/`tools/*` не меняли семантику между 2024-11-05 и 2025-06-18); при проблеме конкретного клиента — точечная правка диспетчера.
- [Агент получает право отправлять произвольные сетевые запросы и менять записи] → это назначение функции; включение явное, порт закрыт токеном, записи под 🔒 агент изменить не может (гарантия живёт в `storage.js`), проекты агенту недоступны для мутаций.
- [Токен в открытом виде в settings.json] → loopback + локальный профиль; риск локального чтения файла равен риску чтения самих данных приложения.
- [Порт занят другим процессом] → статус «ошибка: порт занят» в UI, настройки не сбрасываются, правится без перезапуска приложения.
- [Большой ответ ломает контекст агента] → усечение 100 КБ с пометкой (D8).
- [Своя реализация протокола вместо SDK] → меньше гарантий совместимости с экзотическими клиентами; целевые клиенты проверяются вручную на e2e-этапе.

## Migration Plan

Данных к миграции нет: `settings.json` дополняется необязательной секцией `mcp`, её отсутствие = сервер выключен. Откат — выключить тумблер; полный откат изменения — удалить модуль и каналы, настройки-остатки безвредны (ignorable).

## Open Questions

Нет: порт по умолчанию, лимит усечения и состав инструментов зафиксированы выше; всё остальное — уровень задач.
