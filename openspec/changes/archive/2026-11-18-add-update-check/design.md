# Design: add-update-check

## Context

Сборки распространяются через релизы GitVerse (`https://gitverse.ru/rnikolaenkov/request_lite/releases`). Установленные факты (проверены запросами):
- Публичный API GitVerse (`api.gitverse.ru`) требует `Authorization: Bearer` даже на чтение релизов публичного репозитория (401 анонимно).
- Страницы релизов — Next.js SPA, прямых ссылок на ассеты в HTML нет.
- `electron-updater` не имеет провайдера GitVerse; для macOS требуется код-подпись (Squirrel.Mac), а сборки проекта неподписанные (`identity: null`).

Существующая инфраструктура, которую переиспользуем: IPC-каналы в `src/main/ipc.js` с префиксами, `shell:openExternal` (https-only, уже есть), `app:version`, окно «О приложении» (`AboutDialog.vue`), `settings:get/set` поверх `storage.js` (`DEFAULT_SETTINGS` мержится с сохранёнными настройками).

## Goals / Non-Goals

**Goals:**
- Проверка версии по публичному фиду `latest.json` и уведомление со ссылкой на релиз — на всех трёх платформах, без подписей и токенов.
- Чистое тестируемое ядро (без Electron), покрываемое smoke-тестами.
- Архитектура, из которой позже без переделки UI можно перейти на electron-updater (тот же диалог, другой источник результата).

**Non-Goals:**
- Тихая установка/скачивание обновлений в приложении.
- Код-подпись и нотаризация сборок.
- Чтение релизов из GitVerse API из приложения (нужен токен — отклонено).
- Свой канал распространения фида в коде (публикация фида — ручной/CI-шаг вне приложения).

## Decisions

### 1. Свой update-checker вместо electron-updater
electron-updater не запускается в текущем виде: неподписанный mac-бандл Squirrel.Mac не обновит, а анонимного источника «latest» у GitVerse нет. Свой механизм (fetch JSON + сравнение версий + диалог) — десятки строк, ноль зависимостей, работает везде. Альтернатива «electron-updater сейчас» отложена: вернуться к ней при появлении подписи и публичного статического фида `latest*.yml`.

### 2. Фид — статический `latest.json`, URL — константа в main-процессе
Формат: `{ "version": "0.0.2", "url": "https://gitverse.ru/rnikolaenkov/request_lite/releases/tag/v0.0.2", "notes": "..." }`. Источник истины — `updates/latest.json` в репозитории; при выпуске релиза он обновляется и публикуется по постоянному URL. В коде — константа `UPDATE_FEED_URL` в `update-check.js`: смена хостинга = правка одной строки. Альтернатива «парсить страницу релизов» — отклонена (SPA, нет стабильного DOM/API).

### 3. Чистое ядро в `src/main/update-check.js`
Экспортирует `parseFeed(json)`, `isNewerVersion(feedVersion, currentVersion)`, `checkForUpdate()` (полная проверка с fetch и таймаутом 10 c — по образцу таймаутов `http.js`). Файл не импортирует Electron — `scripts/smoke.mjs` тестирует парсинг и сравнение напрямую. Сравнение версий: только `x.y.z` (числа, ведущий `v` допустим), покомпонентно; всё остальное — ошибка фида, а не «обновления нет».

### 4. IPC: `updates:check` + push-событие `updates:available`
- `updates:check` (invoke) — ручная проверка по кнопке/пункту меню; возвращает `{ status: 'available' | 'upToDate' | 'error', update? , message? }`. Renderer рисует результат в существующем диалоге «О приложении» или в диалоге обновления.
- Автопроверку инициирует main сам (после создания окна, `setTimeout` 5 c, один раз за запуск). Если обновление доступно — `webContents.send('updates:available', update)`; renderer показывает диалог. Ошибки автопроверки в renderer не отправляются.
- Preload: `api.updates.check()` и `api.updates.onAvailable(callback)` по образцу `onMenu`. Переход на страницу релиза — существующий `api.shell.openExternal` (https-only).

### 5. UI: новый `UpdateDialog.vue` + расширение `AboutDialog.vue`
- `UpdateDialog.vue` — по образцу существующих диалогов: overlay, Esc = закрыть, кнопки «Открыть страницу релиза» (primary) и «Закрыть». Показывает новую версию и `notes`.
- `AboutDialog.vue`: кнопка «Проверить обновления…» с индикатором состояния (проверяется / результат / ошибка) и чекбокс «Проверять обновления автоматически» → `settings:set({checkUpdates})`.
- Состояние диалога — в `stores/ui.js` (там уже живут флаги вспомогательных окон).

### 6. Настройка `checkUpdates`
`DEFAULT_SETTINGS` в `storage.js` дополняется `{ checkUpdates: true }` — отсутствие поля в старом `settings.json` автоматически означает «включено» (мерж дефолтов уже реализован). Запись — существующий `setSettings` (атомарная). Чтение перед автопроверкой — из кэша настроек main-процесса.

### 7. Пункт меню «Проверить обновления…»
Клик пункта меню шлёт `updates:check-request` в renderer (по образцу `menu:about` → `onMenu`), ручная проверка выполняется через уже описанный `updates:check` и результат показывается в UI. Так main остаётся без UI-логики, а состояния загрузки видны в renderer.

## Risks / Trade-offs

- [Место публикации фида пока не выбрано] → код изолирован за константой `UPDATE_FEED_URL`; до публикации фида ручная проверка честно вернёт ошибку, автопроверка — тихо промолчит. Хостинг выбирается владельцем (любой статический), шаг зафиксирован в tasks.md как внешний.
- [Компрометация фида (подмена `url`)] → URL из фида валидируется на https, открытие идёт в браузер пользователя; приложение ничего не скачивает и не исполняет. Максимальный ущерб — переход на посторонний сайт.
- [Новый релиз выпущен, а фид не обновлён] → пользователи не узнают об обновлении. Смягчение: обновление фида — обязательный пункт чек-листа релиза (README/tasks).
- [GitVerse разово отдаёт 429 (наблюдалось при агрессивном polling)] → автопроверка раз в запуск, таймаут, ошибки тихие; частота мала для лимитов.
- [Version с 4+ компонентами или префиксами сборок] → фид требует строго `x.y.z`; при таком форматировании релизов проверка вернёт ошибку фида (не ложно-положительное «нет обновлений»).

## Migration Plan

Новая функциональность без изменения данных: расширение `settings.json` обратимо-совместимо. Откат — удаление модуля и IPC-каналов, настройки переносятся безвредно. Процесс релиза после внедрения: поднять `version` в `package.json` → обновить `updates/latest.json` → собрать (`npm run dist:*`) → залить артефакты в релиз GitVerse → опубликовать фид.
