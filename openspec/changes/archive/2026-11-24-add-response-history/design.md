# Design

Мотивация — в proposal.md. Точки входа: ответ формируется в `sendRequest` (`src/main/http.js`, `status/statusText/timeMs/size/headers/body/truncated`) и живёт только в runtime вкладки (`tab.response`, `src/renderer/src/stores/tabs.js`); отправка из UI идёт через IPC `http:request` (`src/main/ipc.js`), из MCP — `send_request` (`src/main/mcp.js`, там же лимит 100 КБ `MCP_BODY_LIMIT`). Хранилище — JSON-файлы, атомарная запись tmp+rename (`writeJsonAtomic`, `src/main/storage.js`).

## Decisions

### D1. История — отдельные файлы, не файл проекта
`storage/history/<projectId>/<requestId>.json` рядом с `projects/`. Причина: история в файле проекта заставляла бы каждую отправку перечитывать и переписывать весь файл (запросы + окружения), соревнуясь со всеми мутациями (drag, Save, MCP-инструменты) — сегодня запись в него и так не сериализована (см. D5). Отдельный файл живёт своим циклом: маленький, пишется только при отправке, удаляется вместе с запросом (`rm` файла) или проектом (`rm` каталога). `createProject` каталог `history/` заранее не создаёт — он появляется с первой записью (mkdir recursive в append).

### D2. Модель записи и лимиты
Файл истории: `{ entries: [...] }`, записи `{ createdAt, response }` от новых к старым. `response` — структура `sendRequest` без изменений плюс поля записи истории: `bodyCut: true` (тело урезано лимитом истории) и `binary: true` с `body: null` (бинарный ответ). Исходный размер остаётся в `response.size`. Константы в `storage.js`: `HISTORY_LIMIT = 10`, `HISTORY_BODY_LIMIT = 100 * 1024` (совпадает с `MCP_BODY_LIMIT` в mcp.js — один и тот же «разумный размер», но без общего импорта: renderer-модуль main-процессу не нужен). Урезание по символам строки, как в `capBody` у mcp.js. `HISTORY_LIMIT` — 10 ответов; при превышении `entries.slice(0, HISTORY_LIMIT)`.

### D3. Бинарность по content-type
Текстовые: `text/*`, `application/json`, `+json`, `application/xml`, `+xml`, `application/javascript`, `application/x-www-form-urlencoded`. Всё остальное — бинарное (`binary: true`, `body: null`). Ответ без content-type считается текстовым — ровно так его показывает и `ResponseView` (ветка raw-text).

### D4. Поток записи
UI: payload IPC `http:request` расширяется до `{ requestId, request, history }`, где `history` — `{ projectId, requestId }` сохранённого запроса или `null`. Заполняет его `sendActive` (`tabs.js`): `projectId` берётся из вкладки, а не из активного проекта — вкладка получает `projectId` при `openSaved` (передаёт `RequestList.vue`, у которого есть активный проект) и при каждом `saveTab` (сейчас `saveTab` пишет в активный проект — вкладка от него и узнаёт свой проект). IPC-обработчик после успешного `sendRequest` **await** `storage.appendResponseHistory(projectId, requestId, response)` — гарантирует, что следующий `history:list` уже видит запись; сбой записи ловится и игнорируется (ответ всё равно возвращается renderer'у — требование «сбой записи не теряет ответ»). MCP: `send_request` вызывает `appendResponseHistory` сам — пара `(projectId, requestId)` у него уже есть; `send_adhoc` историю не пишет.

### D5. Укрепление записи: уникальный tmp + per-file очередь
`writeJsonAtomic` получает уникальный tmp-файл (`<файл>.<uuid>.tmp`) вместо общего `<файл>.tmp`, а все мутации одного пути сериализуются per-file очередью в `storage.js` (по образцу `enqueueMutation` из mcp.js, ключ — абсолютный путь файла). Это закрывает воспроизведённую при анализе гонку: две записи в один файл, начатые в одном тике, смешивались в общий tmp → на диске битый JSON (100 из 100 параллельных пар «запись+reorder» на временной папке). Фича делает запись рутинной (каждая отправка → append), поэтому корректность её AC об атомарности держится на этом решении; попутно закрывается уже существующая гонка на файле проекта. Очередь живёт в `storage.js` (не в mcp.js), чтобы покрывать и IPC, и MCP; чтения остаются вне очереди. Реестр tmp-суффиксов остаётся простым: `.tmp` на конце — очистка не нужна, rename съедает файл; зависший tmp при падении процесса безвреден (следующая запись его не переиспользует).

### D6. Повреждённый файл истории
`readJson` остаётся строгим (CORRUPT_STORAGE, файл не перезаписывается) — новое исключение не вводится. `appendResponseHistory` на CORRUPT_STORAGE тихо пропускает запись (возвращает без изменения файла); `listResponseHistory` пробрасывает ошибку — режим «История» в UI показывает «История недоступна: файл повреждён», остальная работа с запросом не блокируется. Напоминание о ремонте — тот же текст, что у остальных повреждённых файлов.

### D7. Ошибки отправки не пишутся
`appendResponseHistory` вызывается только после успешного `sendRequest` (ветка `ok` в ipc, успешный возврат в mcp) — функция хранилища про ошибки ничего не знает. Таймаут/отмена/сеть/SSL/невалидный URL историю не меняют.

### D8. Renderer: состояние вкладки
Runtime вкладки (`tabs.js`) пополняется: `projectId` (null у несохранённых), `history` (массив записей), а `openSaved` остаётся синхронным — историю подгружает отдельное действие `loadHistory(tabId)` (async): `api.history.list` → `tab.history = entries`, и если история непуста — `tab.response = { ...entry.response, receivedAt: entry.createdAt, fromHistory: true }`. `RequestList.open` после `openSaved` вызывает `loadHistory`. `sendActive` при успехе перезагружает историю (тот же `loadHistory`-запрос) и сбрасывает `fromHistory`; несохранённая вкладка шлёт `history: null`. `cloneTab` копию оставляет без истории (`projectId: null`); `detachSaved` обнуляет и `projectId`, и `history`.

### D9. ResponseView: переключатель и список
`ref('live')`-режим с переключателем «Последний ответ | История» в шапке ответа (стиль `.request-tab`). Режим «История»: вертикальный список записей (время `HH:MM:SS` из `createdAt`, статус-пилл, `timeMs`) + тело/заголовки выбранной записи через существующий конвейер (`prettyJson`/`highlightJson`/`escapeHtml`) — по данным записи, не по `tab.response`; метки «тело урезано до 100 КБ» (`bodyCut`) и «бинарное тело не сохранено» (`binary`). Режим «live» — существующее поведение; если `tab.response.fromHistory`, шапка показывает «из истории» и `receivedAt` (требование «из истории» видно до новой отправки). Файл не хранит выбранный режим между отправками — режим сбрасывается на «live» при новой отправке (ответ меняется целиком).

### D10. Секреты и приватность
В историю пишется **ответ** (заголовки, включая `Set-Cookie`, и тело), а не снимок запроса — подставленные `{{var}}` и токены авторизации на диск не попадают. Сам ответ хранится открытым текстом, как всё хранилище (зафиксировано в AGENTS.md и issue #6: plaintext — осознанное решение). Маскирование секретов — отдельное изменение (issue #6), тут только фиксация границы.

### D11. Что гоняют smoke-тесты
IPC и renderer в smoke не тестируются (Electron). Smoke покрывает слой `storage.js` (append/list/лимиты/бинарь/очистка/повреждённый файл/параллельные записи — на локальном http-сервере секции sendRequest не нужен: записи передаются готовыми объектами) и MCP `send_request` (запись истории через echo-сервер существующей MCP-секции). UI и persist-сценарий «отправил → перезапустил → увидел» — ручной e2e по AGENTS.md.

## Не делаем
- Ручное сохранение «эталонных» ответов (Bruno Save as Example) — автоистория покрывает сценарий сравнения; ручные примеры — отдельная фича при необходимости.
- Diff-визуал между записями — out of scope из issue #3.
- Настройки лимитов в UI — константы кода (AC issue).
- Экспорт истории — out of scope из issue #3.
