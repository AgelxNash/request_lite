# Proposal

## Why

Ответ живёт только в runtime вкладки: после перезапуска приложения прошлый ответ недоступен, а сравнить свежий ответ со старым нельзя. Источник идеи — Bruno, который хранит ответы рядом с запросом. Локальные JSON-файлы позволяют сделать то же без облака и без новых зависимостей (issue #3, roadmap #1 п. 2).

## What Changes

- Автоматическое сохранение последних ответов каждого запроса на диск, отдельно от файла проекта: `storage/history/<projectId>/<requestId>.json`. Ключ истории — пара `(projectId, requestId)`: вкладка получает `projectId` в runtime-состоянии (сейчас `saveTab` пишет в активный проект, а вкладки переживают переключение проекта).
- Запись выполняется в main-процессе сразу после успешной отправки: IPC `http:request` несёт цель истории (проект + сохранённый запрос), MCP-инструмент `send_request` пишет историю тем же кодом хранилища. Ошибки отправки (таймаут, отмена, сеть, SSL, невалидный URL) не сохраняются — только ответы с HTTP-статусом.
- Лимиты — константы, не настройки: 10 последних ответов на запрос; тело в истории урезается до 100 КБ с пометкой (как у MCP-инструментов); бинарные тела (всё, что не text/*, JSON, XML и подобные текстовые типы) не сохраняются.
- UI: переключатель «Последний ответ / История» в `ResponseView`; в режиме истории — список записей (время, статус, длительность) с просмотром выбранной. Открытие сохранённого запроса показывает последний сохранённый ответ со временем его получения (сейчас вкладки не переживают перезапуск — историю видит именно переоткрытый сохранённый запрос).
- Очистка: удаление запроса удаляет файл истории, удаление проекта — каталог истории. Заблокированный запрос историю пишет и хранит — замок защищает содержимое запроса, не ответы.
- Укрепление записи в `storage.js` — в области изменения как условие надёжности фичи: уникальный tmp-файл на запись и per-file очередь мутаций. Сейчас две записи в один JSON, начатые в пределах ~1 мс, смешиваются в общий `<файл>.tmp` (воспроизведено тестами на временной папке: битый JSON на диске). Фича делает асинхронную запись рутинной (каждая отправка), поэтому это условие её acceptance-критерия об атомарности.

## Capabilities

### New Capabilities

- `response-history`: хранение и просмотр последних ответов запроса — автозапись при отправке, лимиты глубины и тела, бинарные ответы, просмотр и восстановление после перезапуска, очистка при удалении, надёжность записи.

### Modified Capabilities

- `request-execution`: требование «Отображение ответа» — пустое состояние остаётся только для несохранённых запросов; переоткрытый сохранённый запрос с историей показывает последний сохранённый ответ с пометкой «из истории» и временем получения.
- `mcp-server`: требование «Отправка запросов через инструменты» — `send_request` сохраняет ответ в историю запроса так же, как отправка из UI; `send_adhoc` историю не пишет.

## Impact

- `src/main/storage.js` — история (`history/` рядом с `projects/`), уникальный tmp + per-file очередь мутаций, очистка при удалении запроса/проекта.
- `src/main/ipc.js`, `src/preload/index.js` — новый префикс `history:*` (`history:list`), payload `http:request` дополняется целью истории.
- `src/main/mcp.js` — `send_request` пишет историю.
- `src/renderer/src/stores/tabs.js` — `projectId` и история в runtime вкладки, загрузка при открытии сохранённого запроса; `RequestList.vue` передаёт projectId; `ResponseView.vue` — переключатель, список, отображение записей.
- `scripts/smoke.mjs` — новый блок «История ответов» (~10 проверок) + проверка `send_request` в MCP-блоке.
- `AGENTS.md` — раскладка хранения, префикс IPC `history:*`, шаги ручного e2e.
- Новых зависимостей нет. История хранится открытым текстом, как всё хранилище: в ответах могут оказаться `Set-Cookie` и токены — осознанное решение, вопрос маскирования секретов трекается issue #6. В историю пишется ответ, а не снимок запроса — подставленные `{{var}}` на диск не попадают.
