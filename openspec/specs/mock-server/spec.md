# mock-server Specification

## Purpose

Встроенный в приложение мок-сервер: пользователь создаёт мок-проекты с настраиваемыми JSON-ответами, запускает один активный сервер и видит журнал принятых запросов. Capability покрывает хранение мок-проектов, жизненный цикл сервера, обработку входящих запросов, журнал и управление всем этим из вкладки «Мок-сервер».

## Requirements

### Requirement: Хранение мок-проектов
Приложение SHALL хранить мок-проекты в JSON-файлах хранилища: индекс всех мок-проектов и отдельный файл для каждого (маршруты и ответ по умолчанию). Пользователь SHALL иметь возможность создать, переименовать и удалить мок-проект; порядок в списке соответствует порядку массива индекса. Данные SHALL сохраняться между запусками приложения. Имя мок-проекта SHALL быть непустым. Активный мок-проект выбирается кликом в списке.

#### Scenario: Создание мок-проекта
- **WHEN** пользователь создаёт мок-проект с непустым именем
- **THEN** он появляется в списке мок-проектов, становится активным, и его данные сохраняются на диске

#### Scenario: Имя не может быть пустым
- **WHEN** пользователь пытается создать или переименовать мок-проект, оставив имя пустым или из одних пробелов
- **THEN** действие отклоняется с ошибкой, данные не изменяются

#### Scenario: Переименование сохраняет содержимое
- **WHEN** пользователь переименовывает мок-проект с уже настроенными маршрутами
- **THEN** имя меняется, маршруты и ответ по умолчанию остаются без изменений и видны после перезапуска приложения

#### Scenario: Удаление с подтверждением
- **WHEN** пользователь удаляет мок-проект и подтверждает действие
- **THEN** запись исчезает из списка, файл и запись индекса удаляются из хранилища

### Requirement: Конфигурация маршрутов мок-проекта
Каждый мок-проект SHALL содержать список маршрутов и ответ по умолчанию. Маршрут задаётся методом (или «любой»), путём (строкой без query-части), HTTP-статусом, списком заголовков ответа, телом ответа (текст) и задержкой в миллисекундах. Путь маршрута SHALL быть непустым, статус — целое 100–599, задержка — целое неотрицательное. Пользователь SHALL сохранять конфигурацию мок-проекта целиком.

#### Scenario: Сохранение конфигурации
- **WHEN** пользователь добавляет и редактирует маршруты и сохраняет мок-проект
- **THEN** маршруты сохраняются на диске и восстанавливаются при повторном открытии мок-проекта и перезапуске приложения

#### Scenario: Маршрут без пути отклоняется
- **WHEN** пользователь пытается сохранить маршрут с пустым путём
- **THEN** сохранение отклоняется с ошибкой, предыдущая конфигурация не изменяется

### Requirement: Запуск и остановка сервера
Приложение SHALL позволять запустить и остановить встроенный HTTP-сервер из вкладки «Мок-сервер». Запуск выполняется для выбранного мок-проекта на указанном порту (целое число 1024–65535). Статус SHALL отражать одно из состояний: остановлен, запущен (с адресом вида `http://127.0.0.1:<порт>`), ошибка (с сообщением).

#### Scenario: Запуск сервера
- **WHEN** пользователь выбирает мок-проект, задаёт порт и запускает сервер
- **THEN** статус становится «запущен» с адресом, и запросы на этот адрес обрабатываются по маршрутам выбранного мок-проекта

#### Scenario: Порт занят другим процессом
- **WHEN** пользователь запускает сервер на порту, занятом другим процессом
- **THEN** статус становится «ошибка» с сообщением о занятом порте, сервер не запущен

#### Scenario: Остановка сервера
- **WHEN** пользователь останавливает запущенный сервер
- **THEN** статус становится «остановлен», порт закрывается, повторное обращение к адресу не отвечает

### Requirement: Не более одного запущенного сервера
В каждый момент SHALL быть запущено не более одного экземпляра мок-сервера: запуск при уже запущенном сервере останавливает его и стартует новый с выбранными мок-проектом и портом. При выходе из приложения запущенный сервер SHALL останавливаться.

#### Scenario: Переключение мок-проекта при работающем сервере
- **WHEN** сервер запущен с одним мок-проектом, и пользователь запускает его же с другим мок-проектом
- **THEN** старый экземпляр останавливается, новый запускается и отвечает по маршрутам нового мок-проекта

#### Scenario: Остановка при выходе из приложения
- **WHEN** пользователь закрывает приложение при запущенном сервере
- **THEN** сервер останавливается, порт не остаётся занятым

### Requirement: Матчинг маршрутов
Запущенный сервер SHALL матчать входящий HTTP-запрос по точному совпадению пути (query-строка игнорируется) и по методу; если метод маршрута не задан, маршрут отвечает на любой метод.

#### Scenario: Ответ по настроенному маршруту
- **WHEN** клиент отправляет запрос, попадающий в маршрут мок-проекта (с точным путём и методом)
- **THEN** сервер отвечает настроенным статусом, заголовками и телом маршрута

#### Scenario: Query-строка не влияет на матчинг
- **WHEN** клиент отправляет запрос на путь маршрута с добавленной query-строкой
- **THEN** запрос матчится по маршруту и получает его ответ

#### Scenario: Маршрут без метода отвечает на любой метод
- **WHEN** у маршрута метод не задан, и клиент отправляет запрос по его пути любым методом
- **THEN** запрос матчится по маршруту

### Requirement: Ответ маршрута и ответ по умолчанию
Ответ на отматченный запрос SHALL состоять из статуса маршрута (по умолчанию 200), его включённых заголовков и его тела; content-type по умолчанию `application/json`, заголовки маршрута перекрывают его. Для неотматченного запроса SHALL отдаваться ответ по умолчанию мок-проекта; если он не настроен — статус 404 с JSON-сообщением об отсутствии маршрута.

#### Scenario: Неотматченный запрос с настроенным ответом по умолчанию
- **WHEN** клиент отправляет запрос, не попадающий ни в один маршрут
- **THEN** сервер отвечает настроенным ответом по умолчанию

#### Scenario: Неотматченный запрос без ответа по умолчанию
- **WHEN** клиент отправляет запрос, не попадающий ни в один маршрут, а ответ по умолчанию не настроен
- **THEN** сервер отвечает 404 с JSON-сообщением об отсутствии маршрута

#### Scenario: Заголовки маршрута перекрывают content-type
- **WHEN** маршрут содержит включённый заголовок `content-type`
- **THEN** ответ содержит значение из заголовка маршрута вместо `application/json`

### Requirement: Задержка ответа маршрута
Задержка маршрута (миллисекунды) SHALL откладывать отправку ответа на указанное время.

#### Scenario: Задержка ответа
- **WHEN** у маршрута задана задержка, и клиент отправляет в него запрос
- **THEN** ответ приходит не раньше указанной задержки, сохраняя настроенное тело и статус

### Requirement: Горячее применение конфигурации
Изменения конфигурации активного мок-проекта SHALL применяться к запущенному серверу без его перезапуска.

#### Scenario: Правка маршрутов на лету
- **WHEN** сервер запущен, и пользователь изменяет и сохраняет маршруты его мок-проекта
- **THEN** следующие запросы отвечают по новой конфигурации без остановки и запуска сервера

### Requirement: Состав записи журнала
Приложение SHALL вести журнал принятых сервером запросов. Каждая запись SHALL содержать время, метод, путь с query-строкой, заголовки запроса и тело запроса; если тело является корректным JSON, оно отображается распарсенным. Запросы, обслуживающие управление сервером из вкладки, в журнал не попадают.

#### Scenario: Запись тела и заголовков
- **WHEN** клиент отправляет запрос с JSON-телом и кастомными заголовками на запущенный сервер
- **THEN** в журнале появляется запись с методом, путём, всеми заголовками запроса и распарсенным телом

### Requirement: Живое обновление и очистка журнала
Записи SHALL появляться в журнале вкладки без обновления вручную. Журнал хранится в памяти с ограничением по количеству записей: при переполнении теряются самые старые. Пользователь SHALL иметь возможность очистить журнал. Журнал не сохраняется между запусками приложения.

#### Scenario: Живое обновление журнала
- **WHEN** на запущенный сервер приходят новые запросы при открытой вкладке «Мок-сервер»
- **THEN** записи появляются в журнале сами, без перезагрузки вкладки

#### Scenario: Переполнение буфера
- **WHEN** число принятых запросов превышает лимит журнала
- **THEN** самые старые записи вытесняются, новые продолжают фиксироваться

#### Scenario: Очистка журнала
- **WHEN** пользователь очищает журнал
- **THEN** список записей становится пустым, последующие запросы продолжают попадать в журнал

### Requirement: Редактор маршрутов во вкладке
Вкладка «Мок-сервер» SHALL отображать для активного мок-проекта редактор маршрутов и ответа по умолчанию: для каждого маршрута редактируются метод (выбор или «любой»), путь, статус, включённые заголовки ответа, тело (текст) и задержка; маршрут можно добавить и удалить. Ответ по умолчанию редактируется как статус и тело. Редактор работает с локальной копией конфигурации, изменения применяются действием сохранения.

#### Scenario: Добавление маршрута
- **WHEN** пользователь добавляет новый маршрут, заполняет метод, путь, статус и тело и сохраняет конфигурацию
- **THEN** маршрут появляется в списке маршрутов мок-проекта и используется сервером при следующих запросах

#### Scenario: Удаление маршрута
- **WHEN** пользователь удаляет маршрут и сохраняет конфигурацию
- **THEN** маршрут исчезает из списка, запросы по его пути начинают отвечать ответом по умолчанию
