# request-execution Specification

## Purpose

Составление и отправка HTTP-запросов с параметрами, заголовками, телом и авторизацией: выполнение строго в main-процессе, конвертация auth и тела в момент отправки, отмена, лимиты и отображение ответа.

## Requirements

### Requirement: Редактирование параметров запроса
Редактор запроса SHALL предоставлять таблицу «ключ — значение» для query-параметров, где каждый параметр включается и отключается галочкой. В момент отправки SHALL включаться только параметры с непустым ключом и включённой галочкой; они дописываются в query string URL. Рядом с вкладкой Params SHALL отображаться счётчик активных параметров.

#### Scenario: Параметры попадают в URL при отправке
- **WHEN** пользователь отправляет запрос с URL `https://api.example.com/users` и включёнными параметрами `page=2` и `limit=10`
- **THEN** сервер получает URL `https://api.example.com/users?page=2&limit=10`

#### Scenario: Отключённый параметр не отправляется
- **WHEN** пользователь отправляет запрос, в котором параметр `debug=1` существует, но его галочка снята
- **THEN** параметр `debug` отсутствует в query string отправленного запроса

#### Scenario: Параметр с пустым ключом игнорируется
- **WHEN** пользователь отправляет запрос, в таблице параметров которого есть строка с пустым ключом
- **THEN** эта строка не попадает в отправленный запрос

### Requirement: Редактирование заголовков запроса
Редактор запроса SHALL предоставлять таблицу «ключ — значение» для заголовков, где каждый включается и отключается галочкой. Новая вкладка SHALL содержать предзаполненные включённые стандартные заголовки: User-Agent, Accept, Accept-Language — их можно менять и удалять. В момент отправки SHALL отправляться только заголовки с непустым ключом и включённой галочкой; включённый заголовок заменяет автозначение клиента. У вкладки Headers SHALL отображаться счётчик активных заголовков.

#### Scenario: Заголовок доходит до сервера
- **WHEN** пользователь отправляет запрос с включённым заголовком `X-Request-Source: postman-lite`
- **THEN** сервер получает заголовок `X-Request-Source` со значением `postman-lite`

#### Scenario: Отключённый заголовок не отправляется
- **WHEN** пользователь отправляет запрос, в котором заголовок `X-Trace` существует, но его галочка снята
- **THEN** сервер не получает заголовок `X-Trace`

#### Scenario: Новая вкладка содержит стандартные заголовки
- **WHEN** пользователь открывает новую вкладку запроса
- **THEN** таблица Headers содержит `User-Agent: PostmanLite/1.0`, `Accept: application/json`, `Accept-Language: ru-RU,ru;q=0.9` — заполненными и с включёнными галочками

#### Scenario: Включённый дефолт заменяет автозначение
- **WHEN** отправляется запрос с включённым дефолтом `User-Agent: PostmanLite/1.0`
- **THEN** сервер получает заголовок `User-Agent: PostmanLite/1.0`, а не автозначение клиента

#### Scenario: Счётчик активных заголовков
- **WHEN** таблица Headers содержит включённые строки с непустыми ключами
- **THEN** рядом с вкладкой Headers отображается их количество

### Requirement: Тело запроса по выбранному типу
Редактор запроса SHALL позволять выбрать тип тела: `none`, `json`, `form-data`, `urlencoded`, `text`. В момент отправки тело SHALL формироваться согласно типу вместе с соответствующим Content-Type: json — `application/json` и текст из редактора; urlencoded — `application/x-www-form-urlencoded` и пары из таблицы; form-data — `multipart/form-data` с границей и текстовыми парами из таблицы (без файлов); text — `text/plain` и текст из редактора; none — запрос без тела.

#### Scenario: JSON-тело с соответствующим Content-Type
- **WHEN** пользователь выбирает тип json, вводит `{"name":"Ann"}` и отправляет запрос
- **THEN** сервер получает тело `{"name":"Ann"}` с заголовком `Content-Type: application/json`

#### Scenario: Urlencoded-тело из таблицы
- **WHEN** пользователь выбирает тип urlencoded с параметрами `grant_type=client_credentials` и `client_id=abc`
- **THEN** сервер получает тело `grant_type=client_credentials&client_id=abc` с заголовком `Content-Type: application/x-www-form-urlencoded`

#### Scenario: Form-data как multipart
- **WHEN** пользователь выбирает тип form-data с параметрами `field1=value1` и `field2=value2`
- **THEN** сервер получает multipart/form-data с обеими парами и корректной границей, Content-Type содержит эту границу

#### Scenario: Текстовое тело без обработки
- **WHEN** пользователь выбирает тип text, вводит произвольный текст и отправляет запрос
- **THEN** сервер получает этот текст без изменений с заголовком `Content-Type: text/plain`

#### Scenario: Тип none не отправляет тело
- **WHEN** пользователь выбирает тип none и отправляет запрос
- **THEN** запрос уходит без тела

### Requirement: Авторизация конвертируется в момент отправки
Редактор запроса SHALL позволять выбрать тип авторизации: `none`, `bearer`, `basic`, `apikey`. Данные авторизации хранятся отдельно от заголовков и SHALL конвертироваться только в момент отправки: bearer — заголовок `Authorization: Bearer <token>`; basic — заголовок `Authorization: Basic <base64(логин:пароль)>`; apikey — ключ и значение, помещаемые либо в заголовок, либо в query-параметр по выбору пользователя.

#### Scenario: Bearer-токен в заголовке
- **WHEN** пользователь выбирает bearer с токеном `t-secret-123` и отправляет запрос
- **THEN** сервер получает заголовок `Authorization: Bearer t-secret-123`

#### Scenario: Basic-креденшалы в base64
- **WHEN** пользователь выбирает basic с логином `user` и паролем `pass`
- **THEN** сервер получает заголовок `Authorization: Basic dXNlcjpwYXNz`

#### Scenario: Apikey в заголовке
- **WHEN** пользователь выбирает apikey с placement «заголовок», ключом `X-Api-Key` и значением `k-42`
- **THEN** сервер получает заголовок `X-Api-Key: k-42`

#### Scenario: Apikey в query
- **WHEN** пользователь выбирает apikey с placement «query», ключом `apiKey` и значением `k-42`
- **THEN** сервер получает query-параметр `apiKey=k-42`

### Requirement: Выполнение запроса в main-процессе
Отправка SHALL выполняться только в main-процессе: renderer вызывает отправку через IPC-мост и не выполняет сетевых запросов сам. Ответ SHALL содержать статус, время выполнения, размер тела, заголовки ответа и тело (до 10 МБ; тело больше лимита обрезается с пометкой об обрезке). При таймауте 30 секунд, ошибке сети или отмене пользователь получает сообщение об ошибке вместо ответа, а интерфейс возвращается в состояние готовности к новой отправке.

#### Scenario: Успешная отправка
- **WHEN** пользователь нажимает Send на доступном URL
- **THEN** область ответа показывает код статуса, время выполнения, размер тела и само тело

#### Scenario: Таймаут
- **WHEN** сервер не отвечает в течение 30 секунд
- **THEN** область ответа показывает ошибку таймаута, кнопка Send снова активна

#### Scenario: Ошибка сети
- **WHEN** пользователь отправляет запрос на недоступный адрес (например, сервер не запущен)
- **THEN** область ответа показывает понятное сообщение об ошибке сети, а не пустой ответ

#### Scenario: Ответ больше лимита
- **WHEN** сервер возвращает тело больше 10 МБ
- **THEN** приложение показывает первые 10 МБ с пометкой, что тело обрезано

### Requirement: Отмена выполняющегося запроса
Во время выполнения запроса кнопка Send SHALL заменяться на Cancel. Отмена SHALL прерывать выполнение запроса и помечать ответ как отменённый.

#### Scenario: Отмена по кнопке
- **WHEN** пользователь нажимает Cancel во время выполнения долгого запроса
- **THEN** выполнение прерывается, область ответа помечает запрос как отменённый, кнопка Send возвращается

### Requirement: Отключение проверки SSL
Редактор запроса SHALL содержать переключатель проверки SSL-сертификата, включённый по умолчанию. При выключенной проверке запросы к серверам с самоподписанными сертификатами SHALL выполняться без ошибки сертификата.

#### Scenario: Самоподписанный сертификат при выключенной проверке
- **WHEN** пользователь выключает проверку SSL и отправляет запрос на сервер с самоподписанным сертификатом
- **THEN** запрос выполняется и возвращает ответ

#### Scenario: Самоподписанный сертификат при включённой проверке
- **WHEN** проверка SSL включена, и сервер использует самоподписанный сертификат
- **THEN** запрос завершается ошибкой сертификата

### Requirement: Отображение ответа
Область ответа SHALL показывать строку статуса (код, время, размер), заголовки ответа и тело ответа. JSON-тело SHALL отображаться отформатированным с подсветкой синтаксиса; не-JSON — как обычный текст. До первой отправки область ответа SHALL показывать пустое состояние.

#### Scenario: JSON-ответ с подсветкой
- **WHEN** сервер возвращает тело с `Content-Type: application/json`
- **THEN** тело отображается отформатированным с подсветкой синтаксиса

#### Scenario: Не-JSON ответ
- **WHEN** сервер возвращает тело `text/plain`
- **THEN** тело отображается как обычный текст без форматирования

#### Scenario: Заголовки ответа доступны
- **WHEN** ответ получен, и пользователь открывает раздел заголовков ответа
- **THEN** отображаются пары «ключ — значение» заголовков ответа
